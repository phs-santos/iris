SIP Bench

Uma bancada de testes SIP no navegador. Você cadastra várias contas, de vários PBX, registra todas de uma vez, liga entre elas e vê na mesma tela o que aconteceu no SIP.

base easy-sipjs 2.7.6 WebRTC + WSS presets asterisk · kamailio · generic nome provisório
O problema

Testar telefonia hoje exige três softphones e paciência

Para validar uma URA, uma fila ou uma transferência, o desenvolvedor costuma abrir um softphone por ramal, alternar entre janelas e caçar o erro num sngrep no servidor. Softphones comuns são feitos para atender cliente, não para testar: escondem o SIP, registram uma conta por vez e não lembram cenários. O SIP Bench inverte isso. Cada conta é um cartão, cada chamada é visível, e o log SIP fica ao lado, filtrado por conta.

Ligar A → B sem trocar de app

Ramal 1001 do PBX de homologação liga para o 2001 do PBX de produção. Os dois lados aparecem na mesma tela.

Testar URA com DTMF

Disca, espera o áudio, manda 1, depois 4321#. Sem procurar o teclado numérico.

Validar um PBX novo

Registra, faz OPTIONS, roda o diagnóstico de WebRTC e mostra o que falhou: certificado, ICE, permissão de microfone.

Reproduzir bug de cliente

Importa o JSON de contas que o colega exportou, repete o cenário e copia o log SIP já sem senha.

Princípios

O que guia as decisões

Uma tela só

Contas, chamadas e log ficam sempre visíveis. Nada importante mora num menu.

Estado em cor e forma

Registro, toque, chamada em espera: cada estado tem um ponto e uma etiqueta reconhecíveis de longe.

Zero SIP para configurar

Ramal, senha, domínio e WSS. O resto vem do preset do easy-sipjs.

Funciona sem PBX

Um modo simulado deixa explorar a interface, demonstrar e testar a própria ferramenta.

Fluxos

Os quatro caminhos mais comuns

Primeiro uso

Abrir→Nova conta→Testar conexão→Salvar e registrar→Ponto verde

Sem PBX à mão, o modo simulado já vem com três contas de exemplo para explorar.

Ligar de uma conta para outra

Selecionar 1001→Atalho "2001 Lab"→Ligar→2001 toca na mesma tela→Auto-atende ou Atender

Os dois cartões de chamada ficam lado a lado. O log intercala os eventos das duas contas por horário.

Testar uma URA

Discar 8000→Ouvir a mensagem→Sequência "1 · espera 2s · 4321#"→Conferir DTMF no log

A sequência aceita pausas e pode ser salva como atalho da conta.

Transferir

Em chamada→Transferir→Cega: digitar destinoouAssistida: escolher outra chamada→Progresso 100/180/200 no cartão

O easy-sipjs já entrega o progresso da transferência pelo NOTIFY, então dá para ver se ela completou de fato.

Arquitetura

Uma instância do easy-sipjs por conta

O app é só front-end. Cada conta cadastrada vira um SipClient próprio, com seu WebSocket e seu registro. Um gerenciador de contas cuida da lista; todos os eventos dos clientes passam por um barramento que alimenta o estado da tela e o log. O modo simulado usa a opção customProvider da biblioteca, então a interface não sabe se está falando com um PBX de verdade.

Pontos de atenção

O que pode atrapalhar

O PBX precisa falar WebRTC

Exige WSS com certificado válido e DTLS-SRTP. PBX só com UDP/TCP fica de fora sem um gateway.

Certificado autoassinado

O navegador recusa o WSS em silêncio. A tela de saúde precisa dizer isso e mostrar o link para aceitar o certificado.

Vários toques ao mesmo tempo

Cada SipClient toca o próprio ringtone. Com auto-atender e várias contas, convém um toque central.

Senhas no navegador

Por padrão a senha não é salva. A exportação em JSON sai sem senha, a menos que o usuário peça.

Para decidir antes de desenvolver

Três escolhas

Qual stack de interface?

Recomendo Vue 3 + Vite + TypeScript: o easy-sipjs já traz um composable Vue e um exemplo nessa stack. Alternativa: HTML e JS puros, num arquivo só.

Web ou desktop no MVP?

Recomendo web, rodando em localhost ou num servidor interno. Desktop fica para depois.

Onde ficam as contas?

Recomendo no navegador, com import/export em JSON. Um servidor de perfis só se o time pedir.
